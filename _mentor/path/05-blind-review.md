<div class="mp-section">
  <h2 id="sec-goals">本阶段目标</h2>

  <h3 class="no_toc" style="font-size:15px;color:#1e40af;margin:0 0 8px;">学生要完成</h3>
  <ul class="mp-goals">
    <li>拿到盲审意见后，先分类、再排序，不要按评审专家写的先后顺序逐条机械回应。</li>
    <li>区分「必须改」和「可以不改但要说明理由」两类意见，把有限的修改时间用在影响通过与否的问题上。</li>
    <li>形成一份可核对的修改说明（Response to Reviewers），逐条对应盲审意见，写清楚改在哪一页、怎么改，或者为什么不改。</li>
    <li>修改说明和论文修改要同步：论文里改了，说明里要能找到；说明里承诺要改的，论文里必须真的改了。</li>
  </ul>

  <h3 class="no_toc" style="font-size:15px;color:#1e40af;margin:16px 0 8px;">导师关注</h3>
  <ul class="mp-goals">
    <li>学生是不是抓住了意见背后真正的问题，而不是只做表面的文字调整。</li>
    <li>修改说明是否让人一眼能看出「改了什么、改没改到位」，方便导师和评委二次核查。</li>
  </ul>

  <p style="margin:16px 0 0;color:#64748b;">
    盲审意见有时写得很重，但目的是帮论文达到应有的质量，不是针对个人。收到意见后的第一反应，建议是先通读一遍、放一放，再回头逐条拆解，会比看完立刻反驳或立刻大改更有效率。
  </p>
</div>

<div class="mp-section">
  <h2 id="sec-types">意见类型怎么分类</h2>
  <p style="margin:0 0 12px;">建议拿到意见后，先按下表把每一条意见归类，再决定处理顺序。</p>
  <div class="mp-table-wrap">
    <table class="mp-table">
      <thead>
        <tr>
          <th style="width:18%;">类型</th>
          <th style="width:47%;">典型表现</th>
          <th style="width:35%;">处理优先级</th>
        </tr>
      </thead>
      <tbody>
        <tr>
          <td>① 结构类</td>
          <td>章节顺序、篇幅分配不合理；Results 和 Discussion 内容混淆；缺少必要章节</td>
          <td>最高：结构问题不改，其他修改容易白做</td>
        </tr>
        <tr>
          <td>② 分析类</td>
          <td>研究问题不具体；案例分析深度不够；结论与前文结果对不上；理论框架用不上</td>
          <td>高：直接影响论文的核心价值</td>
        </tr>
        <tr>
          <td>③ 规范类</td>
          <td>引用格式、参考文献、图表编号、术语一致性、语言表达问题</td>
          <td>中：数量可能很多，但通常改起来更快</td>
          </tr>
        <tr>
          <td>④ 实践描述类</td>
          <td>Project Implementation 交代不清楚（工具、流程、术语筛选标准等）；材料真实性存疑</td>
          <td>高：涉及报告可信度，需要具体补充证据或说明</td>
        </tr>
      </tbody>
    </table>
  </div>
  <p style="color:#64748b;margin:0;">同一条意见常常横跨多个类型，例如「案例分析不够深入」既是分析类问题，也可能提示 Implementation 交代不清楚，导致案例本身缺材料支撑。分类时不必强求唯一归属，重点是找到根源。</p>
</div>

<div class="mp-section">
  <h2 id="sec-bp">Best Practice</h2>
  <div class="mp-qa">
    <h4 class="no_toc">先处理结构和分析类问题，再处理规范类问题</h4>
    <p>如果结构或研究问题本身有大问题，规范类的小修小补很可能因为章节重排、内容调整而白做一遍。建议先确认结构和核心分析没有问题，再统一处理格式、引用、图表编号等规范性修改，效率更高，也不容易漏改。</p>
  </div>
  <div class="mp-qa">
    <h4 class="no_toc">高频扣分点：Implementation 空洞、Results 夹带观点、图表不规范</h4>
    <p>历年盲审意见中反复出现的扣分点集中在三处：Chapter 3 只有笼统的「译前准备、译中翻译、译后校对」流水账，看不出工具、流程和判断依据；Chapter 4 在汇报结果时提前下结论，或者结论里冒出 Chapter 4 没有的新数据；图表缺少编号、说明文字，或者坐标轴截取造成视觉误导。这三类问题都可以对照 <a href="{{ site.baseurl }}/mentor-platform/path/04-report/">04 报告主体写作</a> 的自查清单逐项核对。</p>
  </div>
  <div class="mp-qa">
    <h4 class="no_toc">修改说明按「意见原文—修改情况—定位」三栏写，让人一眼能核对</h4>
    <p>推荐用表格逐条列出：评审意见原文（可摘录关键句）、修改情况说明（改了什么、为什么这样改，或说明未改的理由）、修改位置（第几章第几节、页码）。这样评委或导师复核时，不需要通读全文就能核对每一条是否落实，也是对自己修改工作的一次系统检查。</p>
  </div>
  <div class="mp-qa">
    <h4 class="no_toc">意见看似矛盾时，先找导师沟通，不要自行取舍</h4>
    <p>多位评审专家的意见有时方向不一致（例如一位建议扩大案例数量，另一位建议聚焦分析深度）。遇到这种情况不要自己选一个执行，应主动和导师沟通，确认哪个方向更符合论文当前阶段的实际情况和可行性。</p>
  </div>
</div>

<div class="mp-section">
  <h2 id="sec-qa">Q&amp;A</h2>
  <div class="mp-qa">
    <h4 class="no_toc">Q1 · 意见很多，时间又紧，要不要全部照单全改？</h4>
    <p class="mp-muted">不建议不分主次地全部照改。先按上面的分类表把意见排出优先级，结构和分析类问题优先处理；规范类问题数量可能很多，但通常可以在较短时间内批量解决。如果确实来不及全部完成，应就完成顺序和取舍主动和导师沟通，而不是自己默默决定跳过某些意见。</p>
  </div>
  <div class="mp-qa">
    <h4 class="no_toc">Q2 · 有一条意见我不同意，可以不改吗？</h4>
    <p class="mp-muted">可以，但需要在修改说明里写清楚不改的理由，理由要基于论文本身的事实或逻辑（例如「该案例的原始材料已在保密协议限制下，无法提供更多细节」），而不是简单地说「作者认为不需要修改」。不认同的意见同样要认真回应，敷衍的说明反而容易引发进一步质疑。</p>
  </div>
  <div class="mp-qa">
    <h4 class="no_toc">Q3 · 修改说明要给谁看？格式有要求吗？</h4>
    <p class="mp-muted">修改说明主要给导师核查，部分环节也可能提交给学院或复审专家。学院暂无统一模板，建议采用「意见原文—修改情况—定位」的表格形式，方便他人快速核对，具体格式如导师另有要求，以导师意见为准。</p>
  </div>
  <div class="mp-qa">
    <h4 class="no_toc">Q4 · 盲审意见提到的问题，之前开题时导师没有提过，是不是导师没把好关？</h4>
    <p class="mp-muted">开题阶段和论文全文阶段的评审侧重点不同，开题主要看方向和设计是否可行，全文盲审会更细致地检查案例分析深度、结果呈现规范、语言表达等执行层面的问题。这类问题在开题阶段不容易完全预见，出现新的意见是正常的评审环节，不必理解为「之前没把好关」。</p>
  </div>
</div>

<div class="mp-section">
  <h2 id="sec-check">自查清单</h2>
  <ul class="mp-check">
    <li>已将全部盲审意见按结构 / 分析 / 规范 / 实践描述四类归类，并排出处理优先级</li>
    <li>结构和核心分析类问题已优先处理，不是先改格式再改结构</li>
    <li>已对照 <a href="{{ site.baseurl }}/mentor-platform/path/04-report/">04 报告主体写作</a> 的自查清单，逐项核实 Implementation、Results、图表是否规范</li>
    <li>已形成「意见原文—修改情况—定位」的修改说明，逐条可核对</li>
    <li>不同意的意见已写明具体理由，不是简单地说「不需要修改」</li>
    <li>意见之间出现方向冲突时，已与导师沟通确认取舍</li>
    <li>修改说明中的每一条承诺，论文正文里都能找到对应的实际改动</li>
  </ul>
</div>
